## Stumbles (ranked by cost)

### 1. A "wood gap" diagnosis written into two docs before it was verified
I wrote into `top-need-measure.md` **and** the raven handoff: "*the cell has
no reachable wood; the gatherer can't produce; so phase-4 can't close; so the
chain stops*" — from (a) **one** `[WHY] NO_SPACE job_blocks={}` line and
(b) my model of the gatherer from the job JSON (whose `request:` field is
`None` — the gatherer's targets live in `loot_tables/jobs/…`, which I never
looked at). The user's "help me understand what you mean by wood gap"
triggered the re-check, which found the opposite: **2 of 7 gatherers** were
parked `CANT_REACH`; the other 5 cycled `gather → bop_depositing` and
**extracted a birch_sapling**. The "gap" was a real minority stall, not a
world without wood.
- **Misread signal:** one anchored evidence line + a plausible model of the
  whole class, presented as the cause. This is retro #2's negative-claim
  pattern in positive form — I had been *verifying negatives* but asserting
  **positive causal chains** from a single instance.
- **Pattern:** *writing a diagnosis down (measure doc / handoff) is the
  moment it becomes load-bearing* — those two files are what a future
  session reads first.

### 2. A gate that passed its own verification and then froze the run
The `built(rid) < open(rid)` count gate I wrote to fix the recipe-id latch
correctly built batch-2's `kitchen_stocked` ×3 (my verification evidence),
but the counter is **monotonic** — it never retires when those quests close —
so batch-4's `ks` ×3 were refused (`3 built for 3 open`), the batch never
closed, and the chain's re-eval gap froze the whole run at 2.75. I verified
*the first generation* and shipped the *across-generations* failure. The
retro skill's "enumerate the states it will meet and run each" gate existed;
I ran one state (fresh build). Same family as #1: the passing case is the
benign state.
- Also, I *wrote a stronger claim than the evidence carried* in
  `stall-factors.md` (the batch "never fully closed") and fixed it after —
  caught by re-reading the file before committing.

### 3. Hot-swap assumption: the autotest world is wiped every boot
I launched "run 16c on the SAME world" to hot-swap the builder fixes and
found a fresh seed (1 quest) — `build.gradle` wipes `run/world` in
`doFirst` for *every* autotest `runServer` boot ("clean suite run"). I had
assumed held-run worlds persist across relaunches; the suite's guarantee
says the opposite. Cost: one full launch cycle + a re-plan. Environment
friction — recorded with the exact source location (`build.gradle`
autotest block) so it isn't re-derived.

### 4. Completeness steering (the highest-signal item)
- **"Help me understand what you mean by wood gap."** The user asked an
  *understanding* question, and answering it forced a re-verification that
  broke half my own diagnosis. The steering is the spec: **a causal chain
  I am about to present as a finding is a claim — run the same-source
  check on every link before it enters a doc or a reply.** Task type:
  held-run diagnosis wrap-up → belongs next to retro #2's "why didn't X
  happen?" gate in the held-run skill, and the "verified source" rule in
  AGENTS.md should cover positive causal chains, not just negatives.
- **"Do we know what the top need WAS?"** Correct; answered from the log.
  Smaller nudge; the lesson (read the queue before predicting the beat) is
  a one-liner in this retro only — the data layer was there in two lines.

### 5. Near-miss caught (keep the guard)
- `jmembers` / `javap` returned nothing for `MCQuest` — read the source file
  instead of concluding the API didn't exist. The class-existence trap from
  AGENTS.md held.
